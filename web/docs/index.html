PROJECT HANDBOOK · BETA 1.1.109403

Documentation

A field guide to building, exploring, and contributing to akernel.

Getting started·x86 & x86-64
i

Project status. akernel builds freestanding kernel ELF files. It is not yet a bootable operating system and does not produce a disk image. A bootloader and its required CPU mode and memory mappings are not included.

01 — BEFORE YOU BEGIN

Build requirements

Both architecture targets use the same C source, with separate assembly entry points and linker scripts. You will need:

  • GNU Make
  • GCC with 32-bit compilation support
  • GNU binutils with i386 and x86-64 ELF linkers
  • NASM

02 — BUILD BY HOST OPERATING SYSTEM

Step-by-step build guides

Choose the instructions for the computer you are building on. Linux distributions have separate package-manager steps; Windows uses WSL 2, and macOS uses a disposable Linux VM. These are instructions for compiling the kernel sources, not for assembling a bootable OS image.

  • All build guides and safety notes
  • Ubuntu and Debian Linux
  • Fedora Linux
  • Arch Linux
  • Windows 10/11 with WSL 2
  • macOS with an Ubuntu VM
SafetyThis beta only creates ELF kernel files. It has no bootloader, installer, or ISO; do not write its outputs to a disk or replace your operating system.

06 — THE SOURCE

Project layout

main.cFreestanding kernel entry routine and startup banner.
include/Kernel declarations, error codes, and version metadata.
arch/x86/32-bit entry assembly and linker script.
arch/x86_64/64-bit entry assembly and linker script.
pkg/akernel/Package descriptors, the fetch system-info renderer, and sys interface stub.
releases/Versioned release notes and artifact availability manifests.
web/docs/steps/Standalone build instructions for Linux, Windows, and macOS hosts.
MakefileBuild targets for both ELF architectures.
web/Project landing page, documentation, and visual identity.

The entry points initialize a stack and call kernel_main. The sample writes to VGA text memory at 0xB8000, so a compatible mapping is required from the loader.

07 — PACKAGE STATUS

Packages in this beta

The current package code is metadata and interface scaffolding. It is not an installer, package repository, or complete runtime service. Package sources are not part of the default make targets.

pkg/akernel/package.hCommon package descriptor, version comparison, and target compatibility checks.
pkg/akernel/fetch/Text system-information renderer with compact ASCII artwork; a caller-provided writer handles output.
pkg/akernel/sys/System package descriptor stub; system calls and runtime services are not implemented.
include/akPackage.hKernel version, x86/x86-64, freestanding, and ELF target metadata.

Both sample package descriptors require kernel 1.1.0 or newer, freestanding ELF builds, and a supported x86 architecture. These checks do not install or execute packages.

08 — CONTRIBUTE

Make a contribution

  1. 01

    Fork the repository and clone your fork.

  2. 02

    Create a focused branch, make your changes, and run make.

  3. 03

    Commit the files you changed and push your branch to your fork.

  4. 04

    Open a pull request against oysterzarskyy/akernel.

GITexample workflow
git switch -c my-change
make
git add path/to/changed-files
git commit -m "Describe the change"
git push -u origin my-change

09 — PUBLISH

Beta release 1.1.109403

The versioned release record is in the releases folder ↗. The repository does not yet have a published version tag or GitHub Release. There is also no ISO for this beta: the project has no bootloader, defined boot protocol, or disk-image build target. The release manifest records the planned ISO filename as unavailable; it is not a downloadable artifact.

When publishing source, tag the version and create a GitHub Release. ELF files may be attached as build outputs, clearly labeled as non-bootable kernel scaffolds.

GITbeta 1.1.109403
git tag v1.1.109403
git push origin v1.1.109403

GitHub Pages can publish the forum and this handbook. Enable Settings → Pages → Build and deployment → GitHub Actions in the repository.

10 — COMMUNITY

Forum API and anonymous accounts

The forum front end is connected to the JSON API in api/server.py. The API assigns a persistent anonymous guest identity using a long-lived HttpOnly cookie. The cookie is not readable by page scripts; the browser sends it automatically with requests. Clearing browser cookies loses access to that anonymous identity, so this is not a recoverable registered account.

GitHub Pages cannot run the API process. Host the API separately or put it behind a same-origin reverse proxy, then set the akernel-api-base meta value in web/index.html to the API prefix (for example, https://api.example.com/api).

LOCAL APIPython 3, no external packages
python api/server.py
# Open http://127.0.0.1:8787

For a separately hosted site, configure AKERNEL_ALLOWED_ORIGIN to the exact website origin. Cross-site cookies require HTTPS and these settings:

COOKIE SETTINGSHTTPS deployments only
AKERNEL_ALLOWED_ORIGIN=https://your-site.example
AKERNEL_COOKIE_SAMESITE=None
AKERNEL_COOKIE_SECURE=1

The API currently supports anonymous sessions, listing/filtering discussions, creating discussions, reading a discussion with replies, and posting replies. Data is stored in SQLite at api/forum.sqlite3 by default. Back up this database and put the service behind a production HTTPS reverse proxy before exposing it publicly.
